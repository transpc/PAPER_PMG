# 루프 엔지니어링 프로토콜 (LOOP.md)

> 작성일: 2026-08-09
> 상위 문서: [PLAN.md](PLAN.md) — 전체 계획. 이 문서는 그 계획을 **실행하는 방식**을 정의한다.
> 기록 파일: [LOG.md](LOG.md) — 모든 사이클의 결과가 append 된다.

---

## 1. 개념과 원칙

루프 엔지니어링 = PLAN.md 의 각 Phase 를 **작고 검증 가능한 사이클**로 쪼개어 반복 실행하는 것.

```
┌─> 1 목표 선언 (1문장, 검증 가능한 형태)
│   2 변경 (커밋 가능한 최소 단위)
│   3 실행 (build / test / run — 반드시 in_contain.sh 경유)
│   4 판정 (아래 §2 판정 체계, L1→L2→L3)
│   5 LOG 기록 (§4 규약 — 성공/실패 불문)
└── 6 green → 커밋 후 다음 사이클 / red → §5 실패 처리
```

**원칙**
- **한 사이클 = 하나의 검증 가능한 변화.** 두 가지를 한 번에 바꾸지 않는다 (red 시 원인 분리 불가).
- **모든 사이클은 LOG.md 에 기록된다.** 실패한 사이클일수록 기록 가치가 크다.
- **green 상태에서만 전진.** red 를 안고 다음 사이클로 넘어가지 않는다.
- **냉정 기록.** 결과는 관측된 사실(출력, 수치)만 적는다. 해석·추측은 `추정:` 접두어로 사실과 분리한다. 기대와 다른 결과를 미화하지 않는다.

## 2. 판정 체계

### 핵심 판단 (사용자 결정, 2026-08-09)

> 압력 수정 방정식과 소스(RHS)가 CSR 로 뽑히면 residual 로 작동 여부를 확인할 수 있다.
> 따라서 **수렴에 필요한 반복 횟수(its)를 1차 지표로 작동/오작동을 판정**한다.

CSR 덤프 `(A, b)` 만 있으면 어떤 변경 후에도 `‖b − A·u‖ / ‖b‖` 를 독립적으로 계산해 솔버가 실제로 방정식을 풀었는지 확인할 수 있다 (솔버 자기 보고 잔차에 의존하지 않음). 여기에 its 를 붙이면 "풀긴 푸는데 느려졌다(성능 회귀)"까지 잡힌다. PLAN §4-4 의 bitwise/해 벡터 비교는 이보다 상위의 **마일스톤 검증**으로 격하하고, 매 사이클 판정은 its/residual 로 가볍고 빠르게 돈다.

### 판정 레벨

| 레벨 | 시점 | 내용 | 기준 |
|------|------|------|------|
| **L1 스모크** | 매 사이클 | 빌드 성공, 실행이 비정상 종료 없이 완료 | 컴파일 에러 0, crash/hang 없음 |
| **L2 기능** (1차 판정) | 솔버를 건드린 모든 사이클 | ① 독립 계산 residual `‖b−Au‖/‖b‖ ≤ crit` 도달 ② its 를 ref 와 비교 | 아래 판정표 |
| **L3 골든** | 마일스톤 (Phase 완료, 태그 전) | 해 벡터 비교 — PLAN §4-4 기준 (리팩터링이면 bitwise) | PLAN §4-4 표 |

### L2 판정표

| 판정 | 조건 | 조치 |
|------|------|------|
| **PASS** | 수렴 도달 **and** its == ref (리팩터링) 또는 its ≤ ref (개선 의도 변경) | LOG 기록 → 커밋 |
| **WARN** | 수렴은 하나 its > ref | LOG 에 its 증가량 기록 → 원인 분석 후 진행/롤백 판단 (묵살 금지) |
| **FAIL** | 발산, 정체(maxit 도달), NaN/Inf, 독립 residual 이 crit 초과 | §5 실패 처리 |

### ref_its 기준표

레퍼런스 확보 시점에 아래 표를 채우고, 이후 모든 L2 판정의 기준으로 삼는다. 갱신은 "의도적 알고리즘 개선" 사이클에서만 허용하며 갱신 사유를 LOG 에 남긴다.

| 문제 | rank | 시점/조건 | ref_its | 최종 residual | 채취 사이클 |
|------|------|-----------|---------|---------------|-------------|
| 합성 Poisson 등방 24³ (13,824셀) | 1 | crit=1e-8 | **4** | 3.97e-9 (독립 계산 일치) | C007 |
| 합성 Poisson 이방 24³ (aspect=100) | 1 | crit=1e-8 | **4** | 1.28e-10 | C007 |
| 합성 Poisson 등방 48³ (110,592셀) | 1 | crit=1e-8 | **5** | 1.63e-10 | C007 |
| iSMR ECT 436K셀 (잠정, rv_model=0) | 4 | 초기 과도 step 1~38 | **1~3 (최빈 2)** | ≤ 8.9e-9 | C005-r8 (fort.501, 76솔브) |
| iSMR ECT 덤프 #1 (정식) | 1 | 초기 과도 | (미채취 — rv_model=1 복원 후) | | |
| iSMR ECT 덤프 #2 (정식) | 2, 4 | 준정상 | (미채취) | | |

## 3. 사이클 절차 상세

1. **목표 선언**: "무엇이 어떻게 되면 이 사이클은 성공인가"를 1문장으로. LOG 엔트리의 `목표:` 란에 먼저 쓴다.
2. **변경**: 파일 단위로 최소화. 소스 변경 사이클과 스크립트/인프라 사이클을 섞지 않는다.
3. **실행**: 해당하는 것만 —
   - 인프라 사이클: 스크립트 직접 실행 + DoD 체크 (PLAN §2-3, §3-4)
   - 빌드 사이클: `scripts/build.sh`
   - 솔버 사이클: `pmg_standalone/run_tests.sh` (L2 지표 출력 포함)
   - 케이스 사이클: `scripts/run.sh`
4. **판정**: L1 → (해당 시) L2 → (마일스톤 시) L3. 상위 레벨 실패 시 하위가 green 이어도 red.
5. **LOG 기록**: §4 형식. 실행 명령과 핵심 출력(수치)을 그대로 옮긴다.
6. **마무리**: green → `/git_commit` 으로 커밋. red → §5.

## 4. LOG 규약 (LOG.md)

- **append-only.** 과거 엔트리는 수정하지 않는다 (오기 정정은 새 줄에 `정정:` 으로).
- 사이클 번호 `C###` 는 단조 증가. 실패 후 재시도는 `C###-r1`, `C###-r2`.
- 엔트리 템플릿:

```markdown
## C### | YYYY-MM-DD | <제목>
- 목표: <성공 조건 1문장>
- 변경: <파일 목록 또는 커밋 해시>
- 실행: <명령어 그대로>
- 결과: <관측 사실만 — 출력 요약, its/residual 수치, 소요 시간>
- 판정: PASS | WARN | FAIL — <근거 (레벨별)>
- 다음: <다음 사이클 또는 남은 문제>
```

- L2 해당 사이클은 `결과:` 에 반드시 표 형태로:

```markdown
| 문제 | rank | its (ref) | 독립 residual | 판정 |
|------|------|-----------|---------------|------|
| poisson_iso | 1 | 12 (12) | 3.2e-11 | PASS |
```

## 5. 실패 처리

1. **FAIL 발생** → 같은 번호로 `-r1` 사이클 개시. 목표는 "원인 규명" 자체로 바꾼다.
2. **원인 규명 수단** (순서대로): 변경 diff 재검토 → 이분 탐색(변경 반으로 쪼개 재적용) → `DEBUG= -g -traceback` + `CHECK=` 옵션 빌드 (makefile.in 의 주석 처리된 체크 옵션 활용: `-fpe0`, `-check bounds` 등)
3. **2회 재시도에도 원인 불명** → 롤백(`git checkout` / `revert`)하고 FAIL 상태 그대로 LOG 에 남긴 뒤, 접근 방식을 바꾼 새 사이클 번호로 재계획.
4. 롤백도 사이클이다 — LOG 에 기록한다.

np=900 실패 원인 검증 메모 (2026-08-09, 소스 정독 기준): 원인 **미확정** — C010 의 1차 목표가 재현·확정이다. 검증으로 **약화된 가설**: ① 유닛 누적에 의한 open-file 한계 — 쓰기·읽기 모두 반복마다 CLOSE 확인(`6_subdomain_infor_mg.f90:188,583`, `2_read_mesh_MPI.f90:205`) ② rank 간 유닛 번호 충돌 — Fortran 유닛은 프로세스-로컬이라 성립 안 함. **남은 후보**: 동일 rank(특히 rank 0) 내 유닛 대역 겹침(PLAN §5-1 "유닛 번호 위생"), 고정 크기 배열 한도(`mxnbne` 등), rank 0 직렬 fan-out 의 부하/시간(hang 으로 보일 수 있음), np≥1000 파일명 인코딩(np=900 과는 무관).
